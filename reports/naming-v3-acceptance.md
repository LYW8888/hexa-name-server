# 古籍取名v3交付与验收

按“规则校正→资料入库→候选生成与筛选→全链验收”完成。本轮从用户上传资料出发，复用既有历法、真太阳时、格局旺衰与喜用参考，保留预产期、已出生与先分析现名再推荐改名的三条独立业务流程。

## 已落地

1. **规则校正**：立春年界、喜用优先于补缺、已知笔画差10/11边界、完整五格虚数公式、同句/跨篇出处区分、普通话音节匹配、六维权重归一化和确定性分页。具体规则与项目参数见[data/NAMING_V3.md](../data/NAMING_V3.md)。
2. **资料库**：保留10份原始资料，记录原文件SHA-256；3,636条唯一字典记录、5,543条正文、82个命名片段、121个正向义项。脚本可重建SQLite，原句不匹配或原文件哈希改变就失败，原库不会被半成品覆盖。原始字节不受Git换行转换影响。
3. **生成与筛选**：新表单默认literary_v3；受控组合和编辑义项取代仅在65条固定名字里轮换的限制。支持1–3字名、1–11候选、必用字、避用字、家族避讳、同音避讳、多音姓读法及数理关闭/参考/严格三种模式；跨篇组合明确标识，不冒充古籍原有完整名字。仅在相同分数组内按用字差异优选，保留所有硬条件。
4. **展示与交付**：卡片展示原句、篇章行号、取字类别、康熙笔画、五格三才、全名声调及六维评分。纳音、十二长生与生肖作为辅助资料展示，不叠加命理权重。现名分析、下载报告和主动保存至账号均保留相关依据。

## 本轮修复的体验与隔离问题

- 较长表单快速连续报错时，滚动可能发生在提示显示之前；改为React提交可见提示后再定位，保留字段错误的焦点。
- 新参考库曾要求每个进程创建写锁；改为预构建后只读打开。客户进程仍保持现有目录写权限，不获得命名服务目录的写权限。
- 未记录的字形笔画保留未知，不按部首猜算，不把未收录等同生僻。严格数理模式排除资料不完整的候选，参考模式明确显示缺项。
- “江离”等词中的特定义项不能默认拆作任意组合，限制为原片段使用；显式必用字或喜欢字的选择另行处理。

## 版本与资料边界

- 新表单显式选择literary_v3，省略算法字段的旧客户端保留legacy_v2；历史报告不被改写为新算法结果。
- 121个义项和82个片段是本次可解释候选的基础，不宣称已审核3,636字的全部取名义项。字典未覆盖、繁简合并有歧义的笔画不填造数据。
- 原句“text_matched”是对照用户上传的这版文件；与旧有15处经典原则录文核对分别记录。权重、部首分组、阈值和五格策略是声明的项目规则，匹配值不代表运势。
- 没有可验证的近五年用字频率与姓名总体统计，热度/真实重名概率校正未启用。
- 本轮没有接通真实短信或支付，没有操作线上服务器。

## 部署

在实际代码目录拉取本次提交后，构建前端并导入资料：

```sh
npm ci --prefix frontend
npm run build --prefix frontend
python3 scripts/import_naming_corpus.py
```

然后重启命名服务及客户服务，并重启其他实际调用算法的常驻进程。参考SQLite仅含公开资料，文件0644，隔离服务只读访问；保持客户、客服、财务各自的数据目录与权限。

最后运行 `python3 scripts/check_site.py --url https://实际域名`，核对首页构建与新算法、资料库以及三条业务流程。完整操作见[部署说明](../deploy/README.md)。
