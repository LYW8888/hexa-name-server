# 生成记录、内测完整报告与自愿体验反馈

> 历史版本说明：当前已采用公开限额内测，无需邀请码，联系方式仅展示。最新流程、界面与部署以 [公开内测与工作台](PUBLIC_BETA_QUOTA.md) 为准。


本轮按用户确认的方案实施：**内测用户可先查看完整报告，再自愿提交反馈**。普通免费体验继续只展示名字、读音与简短寓意，完整商业报告仍通过经营者交付。代码已在本地验证，不代表目标服务器已经部署。

## 现在会保存什么

| 动作 | 保存内容 | 保存条件与期限 |
| --- | --- | --- |
| 成功调用生成接口，包括无匹配结果 | 随机生成编号、场景、算法、字数、请求与实际数量、轮次、服务端计算耗时 | 报告服务正常连接时记录；30天；不保存姓名、出生信息或原始IP |
| 普通用户申请经营者报告 | 原有加密完整报告与客户明确提交的资料 | 原流程保持不变，明确同意后保存30天 |
| 内测用户兑换邀请并查看报告 | 加密保存本次出生资料、完整排盘、现名分析、选字与出处、逐名说明 | 同意保存、验证有效邀请与本次生成凭据后；最长30天，实际过期时间页面显示 |
| 用户提交体验表 | 评分、所选问题、改进意见、关联生成编号、体验范围、处理状态 | 自愿点击提交；30天；文字意见加密，不自动公开 |
| 客户主动保存账号记录 | 原有免费名字提案与输入快照 | 沿用账号保存规则；不把内测报告或访问凭据写入客户账号记录 |

生成记录只统计成功返回的生成请求，不等于独立用户数，也不覆盖浏览、表单校验失败或中途离开。自检和自动化请求同样可能计入。它记录服务端耗时，不等同用户从点击到看到结果的完整等待时间。

生成统计与反馈可以关联到用户另行同意保存的内测报告，不能据此承诺整条内测流程完全匿名。普通统计行自身不含姓名、出生资料或原始IP；限流仅保留服务内HMAC摘要。意见表提示用户无需填写出生资料和联系方式。

## 经营者怎么用

1. 登录独立后台，进入“体验反馈与内测”。只向经营者和超级管理员开放，客服、财务与交付岗位不能读取或管理这些资料。
2. 点击“生成一次性内测邀请码”，复制后交给受邀用户。邀请码只在创建响应和当前界面显示，服务仅保存HMAC摘要；关闭后不能再次查回明文，可撤销并重新发码。
3. 邀请在7天内可兑换一份报告。用户先生成提案，再点击“查看完整报告（内测）”，输入邀请码并确认保存范围。
4. 用户可以直接阅读和下载完整报告，也可以不反馈继续使用。提案反馈与报告反馈分开收集、分开统计；只有已获得本次完整内测报告的生成记录才能提交报告范围的反馈。
5. 后台查看原始评分和文字，标记“纳入改进”或“已处理”，按范围和状态筛选，导出当前反馈JSON；不把低分改写成好评。
6. 后台还能查看最近100条生成记录、最近100份内测报告，或按用户提供的报告编号查找并导出完整报告。导出反馈不夹带出生资料或完整报告；完整报告另行导出。
7. 邀请可撤销，内测报告与反馈可独立删除。撤销会阻止后续在线读取，不会清除用户已经阅读、下载的内容；已获得报告的用户仍可提交意见。

用户当前页面持有匿名访问凭据，可在报告有效期内重复查看同一份报告；不自动将凭据或报告存入浏览器长期存储。关闭或刷新页面后，用户可使用已下载文件，或凭报告编号联系经营者找回。页面会明确说明此范围。

## 反馈表与体验边界

评分必须主动选择1–5分，不预填；问题分类和文字意见可选。未看报告的用户评价“免费名字提案”，内测用户阅读后可另行评价“完整内测报告”。两个范围各保存独立草稿，切换范围不会把先前的评分或意见当作新答案。失败重试保留填写内容并复用提交编号，避免重复计数。

邀请码兑换、保存报告与填写反馈是三个明确动作，不要求先评分，不以好评换报告，不将未授权的普通用户切换为免费完整报告用户。匹配数值和传统说明按原算法展示，本轮不新增或改写算法依据。

## 存储与接口边界

沿用独立`report_service.py`进程、私有0700目录、0600数据库、原报告加密密钥与Unix socket的真实调用方UID检查。新增表由服务启动时创建，保留既有报告；没有新的Django身份迁移，也不新增对公网开放的数据库路径。

- `/api/analyze`仍返回限定的免费提案；新增顶层`experience`只包含可用状态、随机生成编号、短期访问凭据和过期时间。生成凭据只在页面内存使用，不进入收藏或客户账号快照。
- 普通接口上的`paid`、`role`、`includeReport`等标记不能解锁报告。
- `POST /api/beta-reports`需要有效邀请码、本次生成凭据、明确同意和与原生成相同的输入及候选；服务端重新计算校验，不接受客户端伪造的报告。
- 同一邀请码只兑换一次；同一生成的安全重试复用原报告，不重复消耗邀请。并发兑换使用数据库事务检查。
- `POST /api/beta-reports/read`只可读取该生成已经授权的内测报告，不能拿普通申请编号遍历经营者报告。邀请和访问凭据不放入URL，HTTP响应禁止缓存。
- `POST /api/experience-feedback`验证本次生成凭据、范围、评分和自愿提交标记，支持幂等重试；不提供公开反馈列表。
- 后台`/api/experience`及其固定管理动作要求经营者身份、动态验证码、首次改密与既有会话/CSRF校验。

生成统计调用使用短超时。报告服务未连接、繁忙或达到记录上限时，生成仍返回名字，`experience.available=false`，页面改为联系经营者反馈。此时不能宣称每次请求都已留存。后台服务不可用会显示错误，不以虚构零值或默认高分代替。

## 部署与验证

需要更新并重启**命名服务、独立管理后台、报告服务**，以及执行前端构建。仅Git拉取或仅刷新前端不会启用新增服务端动作。

```sh
git pull --ff-only origin main
npm ci --prefix frontend
npm run build --prefix frontend
```

报告服务按[原报告部署说明](OPERATOR_REPORTS.md)运行，并保留原密钥、私有目录和身份隔离；不要新建密钥覆盖既有数据。按实际服务名称重启上述进程，确认后台“体验反馈与内测”能读取数据，实际创建邀请并完成一轮内测后再交给用户。生产目标主机尚未由本轮配置。

反向代理后应按原可信代理规则配置`XUMING_TRUST_PROXY=1`，由代理覆盖`X-Real-IP`，应用端口仅监听回环地址；否则统计限流会把所有代理流量归入同一来源。内测验证次数按本次生成凭据隔离，同一办公室或移动网络的其他受邀用户不会被某人的错误输入锁住。

完整回归共 **330项通过**：Python算法、HTTP与报告服务184项，Node规则25项，后台身份与权限29项，客户账号26项，客户端浏览器52项，后台浏览器9项，客户账号浏览器5项。前端构建、实际HTTP站点自检和差异检查通过。

测试覆盖普通提案不泄露报告、匿名记录、低分与批评原文、无默认评分、范围分离、加密、重试、邀请码并发与过期、撤销、后台岗位隔离，以及用户先看报告后自愿反馈的电脑和手机流程。测试在临时目录与模拟岗位身份下运行，不能当作生产主机不同系统账户的隔离验收。
